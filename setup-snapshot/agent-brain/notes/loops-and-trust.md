# Loops and trust

The outer loop chooses useful work from goals, user feedback, project status, and new evidence. The inner loop implements a defined task, checks it against reality, and fixes failures. A third loop improves the method after a repeated failure.

An effective loop needs a target, an observable check, current state, an action that can change that state, and a stopping rule. Repeating an unchanged prompt is not an improvement loop.

Trust attaches to a specific capability and environment. Evidence that a bot can repair a CLI does not establish that it can publish a Roblox game or interpret an ML experiment. Track acceptance, human corrections, escaped defects, duration, and cost per accepted result. PR count and agent count are weak substitutes.

Corrections should land at the level that caused the failure: data structure or interface, executable check, tool, focused skill, then prose preference. Keep the original failing example and verify the repair on a different relevant case. Installing a skill is a proposed improvement until observed outcomes support it.

Analogy: Park sets the destination and what arrival means. The coordinator chooses a route and assigns bounded work. Tools are the vehicle. Verification is the instrument panel. The record lets another driver resume accurately. Removing approval prompts changes access, not the accuracy of the instruments.
